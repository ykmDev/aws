Target Tracking Scaling Policy:
    ASG ရဲ့ average CPU utilization ကို 50% နားမှာ ထိန်းထားဖို့ instances တွေကို အလိုအလျောက် ထပ်တိုးခြင်း၊ လျှော့ချခြင်း ပြုလုပ်ပေး
    Note:
        CloudWatch alarm တစ်ခုတည်းကို configure လုပ်ရုံနဲ့ CPU utilization ကို 50% ဝန်းကျင်မှာ အလိုအလျောက်ထိန်းထားနိုင်မှာ မဟုတ်ပါဘူး။
        CloudWatch Alarm က metric တစ်ခုရဲ့ condition ပြည့်မီခြင်းကို စောင့်ကြည့်ပြီး alarm state ပြောင်းပေးတယ်။
        Scaling Policy က capacity ကို ဘယ်လိုပြောင်းရမလဲဆိုတာ သတ်မှတ်ပေးတယ်။
        Target Tracking Policy က target metric နဲ့ target value ကို အသုံးပြုပြီး လိုအပ်တဲ့ scaling ကို စီမံပေးတယ်။ သက်ဆိုင်ရာ CloudWatch alarms တွေကိုလည်း AWS က အလိုအလျောက်ဖန်တီး၊ စီမံပေးတယ်။
    Scaling Policy လေးမျိုးကို ခွဲခြားမှတ်ပါ:
        Policy	ဘယ်လိုအလုပ်လုပ်သလဲ?	အသုံးပြုသင့်တဲ့အခါ
        Target Tracking	Metric ကို သတ်မှတ်ထားတဲ့ target နားမှာ ထိန်းတယ်	CPU ကို 50% ထားချင်တယ်
        Step Scaling	Alarm breach အဆင့်အလိုက် capacity ကို သတ်မှတ်ထားတဲ့ step တွေနဲ့ ပြောင်းတယ်	CPU မြင့်တဲ့အဆင့်အလိုက် instances ပိုတိုးချင်တယ်
        Simple Scaling	Alarm trigger ဖြစ်ရင် သတ်မှတ်ထားတဲ့ adjustment ကို လုပ်တယ်။ Cooldown က scaling ကို ထပ်လုပ်ခြင်းအပေါ် သက်ရောက်တယ်	အခြေခံ alarm-driven scaling
        Scheduled Scaling	သတ်မှတ်ထားတဲ့ အချိန်ဇယားအတိုင်း capacity ပြောင်းတယ်	နေ့တိုင်း မနက် 9 နာရီ traffic တက်မယ်ဆိုတာ သိထားတယ်
    Memory Trick:
        “Keep CPU at 50%”
            → Target Tracking
        “If CPU exceeds 70%, add 2 instances; if it exceeds 90%, add 4”
            → Step Scaling
        “Scale out every weekday at 9 AM”
            → Scheduled Scaling

            တစ်ချိန်တည်းမှာ internal applications တွေက Kinesis Data Streams ကို consumer အဖြစ်ဖတ်ယူပြီး raw transaction events တွေကို ရရှိနိုင်ပါတယ်။ သတိပြုရန် — ဒီ architecture မှာ raw stream ကို consume လုပ်ခွင့်ရှိတဲ့ application တွေကို sensitive data access အတွက် သင့်လျော်တဲ့ IAM permissions နဲ့ controls တွေ သတ်မှတ်ထားရပါမယ်။
            2. Why are the other options incorrect?
            Option	ဘာကြောင့် မှားသလဲ
            Kinesis Data Firehose + Lambda + DynamoDB	Firehose က streaming data ကို transform လုပ်ပြီး destination ဆီ deliver လုပ်ဖို့ အဓိကရည်ရွယ်ပါတယ်။ Kinesis Data Streams လို multiple independent consumers တွေက stream ကို တိုက်ရိုက် consume လုပ်ဖို့ မသင့်တော်ပါဘူး။
            Raw data → DynamoDB → DynamoDB Streams	DynamoDB မှာ item အသစ်ရေးတိုင်း sensitive fields တွေကို auto-remove လုပ်ပေးမယ့် built-in rule မရှိပါဘူး။ Lambda trigger နဲ့ cleansing လုပ်နိုင်ပေမဲ့ raw data ကို အရင်သိမ်းပြီးမှ update လုပ်ရတာကြောင့် ဒီ use case အတွက် မသင့်တော်ပါဘူး။
            S3 batch files → Lambda → DynamoDB	Batch processing က data စုဆောင်းပြီးမှ လုပ်ဆောင်တာဖြစ်လို့ near-real-time requirement နဲ့ မကိုက်ညီပါဘူး။
            Kinesis Data Streams + Lambda + DynamoDB	Correct. Streaming events တွေကို near-real-time process လုပ်နိုင်ပြီး multiple consumers တွေကလည်း data stream ကို အသုံးပြုနိုင်ပါတယ်။
            3. Kinesis Data Streams vs Kinesis Data Firehose
            Feature	Kinesis Data Streams	Kinesis Data Firehose
            Main purpose	Real-time stream ingestion and consumption	Streaming data delivery
            Multiple consumers	Yes	Not a general-purpose multi-consumer stream
            Consumer reads records	Yes	Consumer apps generally don't read from Firehose as a retained stream
            Lambda processing	Lambda can consume the stream	Lambda can transform records during delivery
            Data destination	Consumers decide what to do with records	Configured delivery destination(s)
            Best use case	Multiple apps process the same events	Deliver transformed streaming data to a destination
            အရေးကြီးတဲ့ nuance: Firehose မှာ Lambda transformation ကို အသုံးပြုနိုင်ပေမဲ့ ဒီမေးခွန်းမှာ internal applications အများအပြားက raw transactions ကို stream တစ်ခုတည်းကနေ consume လုပ်ရမှာဖြစ်လို့ Data Streams က ပိုသင့်တော်ပါတယ်။
            4. Exam memory trick
                Kinesis Data Streams
                Multiple consumers · Near-real-time processing · Replay within retention

                Kinesis Data Firehose
                Transform and deliver streaming data to destinations

                DynamoDB
                Low-latency NoSQL document/key-value access

                စာမေးပွဲမှာ မှတ်ထားရမယ့် rule:
                - Near-real-time + multiple consumers → Kinesis Data Streams
                - Transform + deliver to a destination → Kinesis Data Firehose
                - Remove sensitive data from each event → AWS Lambda
                - Low-latency NoSQL retrieval → Amazon DynamoDB

        လုပ်ရပါတယ်။

EC2 Instance Connect ဘယ်လိုအလုပ်လုပ်သလဲ?
    1. Developer က AWS Management Console မှာ EC2 instance ကိုရွေးတယ်။
    2. Connect → EC2 Instance Connect ကိုနှိပ်တယ်။
    3. EC2 Instance Connect က temporary public key ကို instance ဆီ ပို့ပေးတယ်။
    4. SSH client က corresponding private key နဲ့ authentication လုပ်ပြီး connection တည်ဆောက်တယ်။
    5. Temporary public key က instance ရဲ့ authorized_keys ထဲမှာ အချိန်တိုအတွင်းသာ အသုံးပြုနိုင်တယ်။
    ပုံမှန်အားဖြင့် public key ကို instance ပေါ်မှာ 60 seconds ခန့်သာ authorize လုပ်ထားပါတယ်။ 
    ဒီအချိန်က SSH connection ကိုယ်တိုင် 60 seconds ပြီးရင် ပိတ်သွားတယ်လို့ မဆိုလိုပါဘူး။

RDS Multi-AZ မှာ Primary DB ပျက်သွားရင် AWS က အလိုအလျောက် Failover လုပ်ပေးပြီး Database Endpoint (URL) က မပြောင်းပါဘူး
    Primary failure → Automatic Failover
    Standby DB ကို Primary အဖြစ် promote လုပ်ပြီး RDS Endpoint ရဲ့ DNS CNAME ကို instance အသစ်ဆီ ညွှန်ပေးပါတယ်။
    Failover ဖြစ်တဲ့အခါ အဆင့်ဆင့်
        1. Primary DB instance ပျက်သွားတယ်။
        2. Amazon RDS က failure ကို detect လုပ်တယ်။
        3. Standby DB ကို Primary အဖြစ် promote လုပ်တယ်။
        4. RDS ရဲ့ DNS CNAME record ကို update လုပ်ပြီး Endpoint က DB အသစ်ဆီ ညွှန်ပေးတယ်။
        5. Application က အရင် Endpoint အမည်အတိုင်း ပြန် connect လုပ်နိုင်တယ်။
    သတိပြုရန် — Failover က အလိုအလျောက်ဖြစ်ပေမဲ့ ချက်ချင်းပြီးတာမဟုတ်ပါဘူး။ ပုံမှန်အားဖြင့် မိနစ်အနည်းငယ်ကြာနိုင်ပြီး Application က connection ပြန်တည်ဆောက်ဖို့ လိုနိုင်ပါတယ်။

EC2 instances တွေကို patch လုပ်နေချိန်မှာ ALB က user traffic မပို့အောင် အလိုအလျောက်ထိန်းချုပ်ပေးဖို့
    Option 1 — AWSEC2-PatchLoadBalancerInstance
            ဒီ Automation document က Load Balancer နဲ့ချိတ်ထားတဲ့ EC2 instance ကို patch လုပ်တဲ့အခါ 
            အန္တရာယ်ကင်းအောင် အဆင့်ဆင့်လုပ်ဆောင်ပေးဖို့ ရည်ရွယ်ထားတာပါ။ 
            ALB, NLB နဲ့ Classic Load Balancer တွေကို support လုပ်ပါတယ်။ 
            AWS Systems Manager Automation Runbook Reference
                1. Check health — Instance က healthy ဖြစ်နေတာကို စစ်ဆေးတယ်။
                2. Deregister — Instance ကို Load Balancer target group ကနေ ယာယီဖယ်ရှားတယ်။
                3. Connection draining — လက်ရှိဆောင်ရွက်နေတဲ့ request တွေ ပြီးဆုံးဖို့ သတ်မှတ်ထားတဲ့အချိန်ကို စောင့်တယ်။
                4. Patch — AWS-RunPatchBaseline ကို အသုံးပြုပြီး patch လုပ်တယ်။
                5. Re-register — Instance ကို Load Balancer ထဲ ပြန်ထည့်တယ်။
            ဒီလိုလုပ်ခြင်းက patching ကြောင့် instance တစ်လုံး ယာယီ unavailable ဖြစ်နေချိန်မှာ request အသစ်တွေ 
            အဲဒီ instance ဆီ မရောက်အောင် ကာကွယ်ပေးပါတယ်။
    Option 2 — Systems Manager Maintenance Windows
        Maintenance Windows က ဘယ်အချိန်မှာ patch လုပ်မလဲ ဆိုတာကို schedule သတ်မှတ်ပေးတဲ့ feature ဖြစ်ပါတယ်။ 
        Automation runbook ကို Maintenance Window task အဖြစ် register လုပ်ပြီး သတ်မှတ်ထားတဲ့အချိန်မှာ အလိုအလျောက် run စေနိုင်ပါတယ်
    Note:
        AWS feature	အဓိကတာဝန်:
        AWSEC2-PatchLoadBalancerInstance	Instance ကို deregister လုပ်ခြင်း၊ drain လုပ်ခြင်း၊ patch လုပ်ခြင်း၊ ပြန် register လုပ်ခြင်း
        Systems Manager Maintenance Windows	Patching ကို ဘယ်အချိန်မှာ run မလဲ၊ ဘယ် target တွေကို လုပ်မလဲဆိုတာ schedule/orchestrate လုပ်ခြင်း
    
Kinesis Data Streams — PutRecords Batch Processing:
    အဓိကက Kinesis Data Streams ထဲကို record တွေကို တစ်ခုချင်းစီ ပို့နေတဲ့အတွက် API request overhead များနေခြင်းကို ကုန်ကျစရိတ်အနည်းဆုံးနဲ့ ဘယ်လိုဖြေရှင်းမလဲ ဆိုတာပါ။
        1. ဘာကြောင့် ProvisionedThroughputExceededException ဖြစ်တာလဲ?
        Amazon Kinesis Data Streams မှာ data တွေကို shards တွေကနေတစ်ဆင့် လက်ခံပါတယ်။ Shard တစ်ခုစီမှာ write throughput limit ရှိပါတယ်။
        ပုံမှန်အားဖြင့် provisioned shard တစ်ခုမှာ—
        - Write throughput: 1 MB/second
        - Write rate: 1,000 records/second
        ဒီ limit ကို ကျော်လွန်သွားရင် ProvisionedThroughputExceededException ဖြစ်နိုင်ပါတယ်။
    PutRecord နဲ့ PutRecords က ဘာကွာလဲ?
            PutRecord — တစ်ခုချင်းစီပို့ခြင်း
                Record 100 ခုအတွက် API request 100 ခု လိုအပ်နိုင်ပါတယ်။ Request overhead ပိုများပြီး 
                API call rate limit ကို မြန်မြန်ထိနိုင်ပါတယ်။
            PutRecords — Batch လုပ်ပြီးပို့ခြင်း
                API request တစ်ခုမှာ records အများအပြား ထည့်ပို့နိုင်ပါတယ်။ Request overhead ကို လျှော့ချနိုင်ပြီး 
                API request throughput ကို ပိုမိုထိရောက်စွာ အသုံးပြုနိုင်ပါတယ်။

AWS Transfer Family + Amazon EFS:
    အဓိက စဉ်းစားရမယ့် requirement ၅ ခုရှိပါတယ်။
        - Serverless / Fully managed — EC2 instances တွေကို ကိုယ်တိုင် manage မလုပ်ချင်ဘူး။
        - SFTP — External partners တွေက SFTP နဲ့ file upload/download လုပ်ရမယ်။
        - Shared file system — EC2 instances နှစ်ခုက လက်ရှိ shared storage ကို အသုံးပြုနေတယ်။
        - Fine-grained permissions — Linux လို user တစ်ယောက်ချင်းစီအလိုက် file access ခွဲခြားချင်တယ်။
        - IP-based restrictions — Trusted IP addresses တွေကနေပဲ ချိတ်ဆက်ခွင့်ပြုချင်တယ်။
    ဒီ requirement တွေကို ပေါင်းစပ်ဖြည့်ဆည်းပေးနိုင်တဲ့ solution က AWS Transfer Family + Amazon EFS ဖြစ်ပါတယ်။
    Service တစ်ခုချင်းစီရဲ့ တာဝန်
        AWS service / feature	ဘာလုပ်ပေးသလဲ?
        AWS Transfer Family	SFTP server infrastructure ကို AWS က manage လုပ်ပေးတယ်။
        Amazon EFS	Shared file system ကို ပေးတယ်။ EC2 နှစ်လုံးအစား EFS ကို Transfer Family က တိုက်ရိုက်အသုံးပြုနိုင်တယ်။
        Elastic IP	External partners တွေအတွက် တည်ငြိမ်တဲ့ public IP addresses ပေးတယ်။
        Security Group	Trusted partners တွေရဲ့ source IP addresses တွေကိုသာ SFTP port 22 မှာ ခွင့်ပြုတယ်။
        POSIX identity mapping	User တစ်ယောက်ချင်းစီအတွက် UID, GID နဲ့ directory permissions သတ်မှတ်ပေးတယ်။
        IAM policies	Transfer Family က EFS ကို အသုံးပြုခွင့်နဲ့ သက်ဆိုင်ရာ AWS resource permissions တွေကို ထိန်းချုပ်တယ်။
        AWS Transfer Family က Amazon S3 နဲ့ Amazon EFS ကို native storage backend အဖြစ် ပံ့ပိုးထားပါတယ်။ 
        EFS ကို သုံးတဲ့အခါ POSIX user/group IDs နဲ့ file permissions တွေကို အသုံးပြုနိုင်ပါတယ်။ 
    3. ဘာကြောင့် Amazon EFS ကို ရွေးရတာလဲ?
        ကုမ္ပဏီရဲ့ လက်ရှိ architecture မှာ EC2 Linux instances နှစ်လုံးက shared file system တစ်ခုကို အသုံးပြုထားပါတယ်။ ဒီအချက်က အရေးကြီးပါတယ်။
        - Shared storage: EC2 နှစ်လုံးနဲ့ ချိတ်ဆက်ထားတဲ့ file system ပုံစံကို ဆက်လက်ထိန်းသိမ်းနိုင်တယ်။
        - POSIX permissions: Linux user တစ်ယောက်စီရဲ့ file ownership နဲ့ directory access ကို UID/GID နဲ့ ထိန်းချုပ်နိုင်တယ်။
        - Elastic scaling: File storage capacity က data တိုးလာတာနဲ့အမျှ အလိုအလျောက် တိုးချဲ့နိုင်တယ်။
        - Less operational overhead: SFTP အတွက် EC2 instances တွေကို ကိုယ်တိုင် patch လုပ်တာ၊ server maintenance လုပ်တာတွေ လျှော့ချနိုင်တယ်။
        - Encryption: EFS encryption at rest ကို enable လုပ်နိုင်ပြီး SFTP က transfer လုပ်တဲ့ data ကိုလည်း encrypted connection ဖြင့် ပို့နိုင်တယ်။
Sporadic bursts/occasional bursts
    ရံဖန်ရံခါ ပေါ်ပေါက်လာသော လှုပ်ရှားမှုများ

    EFS ကို ဘယ်အချိန်မှာ အသုံးပြုသလဲ?
        Shared network file system
        EC2 instances နှစ်ခုစလုံးက EFS ထဲရှိ shared files များကို access လုပ်နိုင်တယ်။

        EFS ရဲ့ အဓိကအင်္ဂါရပ်တွေကတော့
            - Shared storage: Compute instances အများအပြားက file system တစ်ခုတည်းကို access လုပ်နိုင်တယ်။
            - Elastic capacity: Storage capacity ကို ကိုယ်တိုင် volume size သတ်မှတ်ပြီး ကြိုတင်တိုးချဲ့စရာ မလိုဘဲ data အလိုက် တိုးလာနိုင်တယ်။
            - Managed service: AWS က file system infrastructure ကို စီမံပေးတယ်။
            - NFS: Linux workloads တွေက ပုံမှန်အားဖြင့် NFS protocol ကိုသုံးပြီး mount လုပ်တယ်။
            - Multi-AZ availability: EFS Regional file system က data ကို multiple AZs အတွင်း redundant သိမ်းဆည်းပေးတယ်။
            EFS ဟာ block storage မဟုတ်ဘဲ file storage ဖြစ်ပါတယ်။ EC2 တစ်လုံးအတွက် block storage လိုအပ်ရင် EBS ကို စဉ်းစားပါ။
            2. EFS Storage Classes — ဘယ် data အတွက် ဘယ် class ကိုသုံးမလဲ?
            Storage class ဆိုတာ file data ကို ဘယ်လိုသိမ်းဆည်းပြီး storage cost နဲ့ access performance ကို ဘယ်လိုချိန်ညှိမလဲ ဆိုတာပါ။ 

        1. EFS Standard
            Frequently accessed
            - မကြာခဏ ဖတ်ရှု၊ ရေးသားရတဲ့ active files တွေအတွက်။
            - Sub-millisecond first-byte read latency ကို ရည်ရွယ်ထားတယ်။
            - Web applications, shared working files, active research datasets တွေအတွက် သင့်တော်တယ်။

        2. EFS Infrequent Access (IA)
            Infrequently accessed
            - တစ်ခါတစ်ရံမှသာ access လုပ်တဲ့ files တွေအတွက်။
            - Standard ထက် storage cost သက်သာနိုင်တယ်။
            - File access နဲ့ data retrieval အတွက် ထပ်ဆောင်း charges ရှိနိုင်တယ်။

        3. EFS Archive
            Rarely accessed
            - တစ်နှစ်အတွင်း အကြိမ်အနည်းငယ်သာ access လုပ်တဲ့ cold data အတွက်။
            - IA ထက် storage cost ပိုသက်သာနိုင်တယ်။
            - Access latency နဲ့ retrieval charges ကို ထည့်စဉ်းစားရမယ်။
            - Regional EFS နဲ့ Elastic Throughput လိုအပ်တယ်။

        Regional နဲ့ One Zone storage classes
            Storage class	Data location	Exam မှာ မှတ်ရန်
            Standard	Multiple AZs	Active data + high availability
            Standard-IA	Multiple AZs	Infrequent access + lower storage cost
            Archive	Multiple AZs	Rarely accessed, long-term file data
            One Zone	Single AZ	Lower cost, AZ failure risk ပိုများ
            One Zone-IA	Single AZ	Infrequent access + single-AZ storage
            Regional file systems က data ကို multiple Availability Zones အတွင်း redundant သိမ်းဆည်းပေးတယ်။ One Zone က AZ တစ်ခုတည်းမှာ သိမ်းဆည်းတာကြောင့် အဲဒီ AZ တစ်ခုလုံး ထိခိုက်တဲ့ disaster မှာ data loss risk ရှိတယ်။ 

        အရေးကြီးတဲ့ concept — Lifecycle Management
            EFS Lifecycle Management ကိုသုံးပြီး မကြာသေးခင်က access မလုပ်ထားတဲ့ files တွေကို Standard ကနေ IA သို့မဟုတ် Archive သို့ အလိုအလျောက် ပြောင်းနိုင်တယ်။ လိုအပ်ရင် Intelligent-Tiering နဲ့ access pattern ပြန်ပြောင်းလာတဲ့ data ကို Standard သို့ ပြန်ရွှေ့နိုင်တယ်။ 

            ဥပမာ — Genomics project မှာ လက်ရှိတွက်ချက်နေတဲ့ data ကို Standard မှာထားပြီး၊ လအတော်ကြာ မသုံးတဲ့ research files တွေကို IA သို့ ရွှေ့နိုင်တယ်။
            3. EFS Performance Modes
            Performance mode က file operations တွေရဲ့ latency နဲ့ parallel workload အပေါ် EFS ဘယ်လိုအလုပ်လုပ်မလဲ ဆိုတာကို သတ်မှတ်ပေးတယ်။
            Performance mode	ဘယ်အချိန်မှာသုံးမလဲ
            General Purpose	Low latency လိုအပ်တဲ့ workload အများစုအတွက်၊ AWS က အကြံပြုထားတဲ့ default mode
            Max I/O	ယခင်က အလွန် parallel ဖြစ်တဲ့ workload တွေအတွက် သုံးခဲ့တဲ့ mode၊ latency ပိုမြင့်နိုင်ပြီး ယခု configuration အသစ်များမှာ ကန့်သတ်ချက်ရှိတယ်
            AWS ရဲ့ လက်ရှိ recommendation က General Purpose ဖြစ်ပါတယ်။ Max I/O ကို One Zone file systems နဲ့ Elastic Throughput အသုံးပြုတဲ့ file systems တွေမှာ မပံ့ပိုးပါဘူး။ 

            Exam tip: “Low latency” ဆိုရင် General Purpose ကို အရင်စဉ်းစားပါ။

        4. EFS Throughput Modes — Exam မှာ အရေးအကြီးဆုံးအပိုင်း
            Throughput mode က EFS က data ကို ဘယ်လောက်မြန်မြန် ဖတ်ရှု/ရေးသားပေးနိုင်မလဲ၊ throughput ကို ဘယ်လိုသတ်မှတ်မလဲ ဆိုတာနဲ့ သက်ဆိုင်တယ်။
            လက်ရှိ AWS documentation မှာ Throughput modes သုံးမျိုးရှိတယ် — Elastic, Bursting, Provisioned။ Elastic က default ဖြစ်ပြီး workload အများစုအတွက် AWS က အကြံပြုထားပါတယ်။ 

            1. Elastic Throughput
            Default / Recommended
            - Workload လိုအပ်ချက်အလိုက် throughput ကို အလိုအလျောက် တိုး၊ လျှော့ပေးတယ်။
            - Peak throughput ကို ကြိုတင်သတ်မှတ်စရာမလိုဘူး။
            - Unpredictable spikes နဲ့ bursty workloads တွေအတွက် သင့်တော်တယ်။
            - Throughput အသုံးပြုမှုအပေါ် မူတည်ပြီး ကုန်ကျစရိတ်ရှိတယ်။
            Example: Genomics analysis အတွက် ဘယ်အချိန် throughput မြင့်မယ်ဆိုတာ မသိတဲ့အခါ။

            2. Bursting Throughput
            - EFS Standard မှာရှိတဲ့ data ပမာဏအပေါ် မူတည်ပြီး baseline throughput ရရှိတယ်။
            - Throughput credits ကို စုဆောင်းပြီး လိုအပ်ချိန်မှာ burst လုပ်နိုင်တယ်။
            - Average usage နည်းပြီး ခဏတာ throughput မြင့်ဖို့လိုတဲ့ workload တွေအတွက် သင့်တော်နိုင်တယ်။
            - Credits ကုန်သွားရင် burst capacity ကန့်သတ်ခံရနိုင်တယ်။
            Example: အချိန်အများစု idle ဖြစ်ပြီး ခဏတာ data processing လုပ်တဲ့ workload။

            3. Provisioned Throughput
            - File system size နဲ့ မသက်ဆိုင်ဘဲ လိုချင်တဲ့ throughput ပမာဏကို သတ်မှတ်နိုင်တယ်။
            - Throughput လိုအပ်ချက်ကို ကြိုတင်သိထားတဲ့ workload အတွက် အသုံးဝင်တယ်။
            - Provision လုပ်ထားတဲ့ throughput အတွက် အပိုကုန်ကျစရိတ် ရှိနိုင်တယ်။
            Example: တစ်နေ့လုံး throughput မြင့်မြင့်နဲ့ အချိန်ကြာကြာ အလုပ်လုပ်ရတဲ့ workload။

ဒီမေးခွန်းမှာ အဓိကက Website clickstream data ကို traffic spike များတဲ့အချိန်မှာပါ data မပျောက်စေဘဲ လက်ခံနိုင်ရမယ်၊ real-time analytics လုပ်နိုင်ရမယ်၊ infrastructure ကိုလည်း decouple လုပ်ပြီး scale လုပ်နိုင်ရမယ် ဆိုတာပါ။

SNI ဆိုတာဘာလဲ?
    SNI (Server Name Indication) ဆိုတာ TLS handshake လုပ်တဲ့အချိန် client က ဘယ် hostname ကို ချိတ်ဆက်လိုတယ်ဆိုတာ server ကို အသိပေးတဲ့ TLS extension ဖြစ်ပါတယ်။

    ဥပမာ -
    - checkout.mycorp.com → Checkout အတွက် certificate
    - www.mycorp.com → Website အတွက် certificate
    - yourcorp.com → သက်ဆိုင်ရာ certificate
    ALB ရဲ့ HTTPS listener မှာ certificate အများအပြားကို attach လုပ်ထားနိုင်ပါတယ်။ Client က hostname ကို SNI မှတစ်ဆင့် ပေးပို့တဲ့အခါ ALB က သင့်တော်တဲ့ certificate ကို ရွေးချယ်ပေးပါတယ်။

    အရေးကြီးချက်: SNI က certificate ရွေးချယ်ပေးတာဖြစ်ပြီး request ကို target group ဆီပို့ပေးတာက ALB ရဲ့ listener rules ဖြစ်ပါတယ်။ အောက်ပါ URL တွေကို path-based routing နဲ့လည်း ခွဲပို့နိုင်ပါတယ်။
    - yourcorp.com/profile → Profile target group
    - yourcorp.com/search → Search target group
Use SSL certificates with SNI:
    ALB တစ်ခုတည်းမှာ certificate အများအပြား attach လုပ်ပြီး domain အလိုက် certificate ရွေးချယ်နိုင်ပါတယ်။
    ဘာကြောင့် မရွေးသင့်သလဲ
    Change ELB SSL Security Policy: TLS versions နဲ့ cipher suites စတာတွေကို သတ်မှတ်ပေးတာပါ။ Domain အများအတွက် certificate ခွဲရွေးပေးတဲ့ ဖြေရှင်းချက်မဟုတ်ပါ။
    Use a wildcard SSL certificate: *.mycorp.com က checkout.mycorp.com နဲ့ www.mycorp.com လို subdomains တွေအတွက် အသုံးဝင်ပါတယ်။ ဒါပေမဲ့ yourcorp.com ဆိုတဲ့ အခြား domain ကို အလိုအလျောက် cover မလုပ်ပါဘူး။
    Use an HTTP to HTTPS redirect: HTTP request ကို HTTPS သို့ redirect လုပ်ပေးတာပါ။ Domain အများအတွက် မတူညီတဲ့ certificates ကို ရွေးချယ်ပေးတဲ့နည်းလမ်း မဟုတ်ပါ။

            3. သတ်မှတ်ထားတဲ့ rules အရ ဘယ် target တွေဆီ ပို့မလဲ ဆုံးဖြတ်တယ်။
            4. သက်ဆိုင်ရာ AWS services သို့မဟုတ် third-party SaaS partner တွေဆီ event ကို route လုပ်ပေးတယ်။
                ဒါကြောင့် application တစ်ခုနဲ့တစ်ခု တိုက်ရိုက်ချိတ်ဆက်ပြီး အမြဲတမ်းအပြန်အလှန်စောင့်ဆိုင်းနေဖို့ မလိုတော့ပါဘူး။
            2. EventBridge vs SQS vs SNS vs ELB
            Service	အဓိကအသုံးပြုမှု	ဒီမေးခွန်းမှာ
                Amazon EventBridge	Event-driven architecture, SaaS integrations, event filtering and routing	အဖြေမှန်
                Amazon SQS	Queue ထဲမှာ message သိမ်းထားပြီး consumer က process လုပ်ခြင်း	Queue-based decoupling အတွက် ကောင်းပေမဲ့ SaaS integration က အဓိကလိုအပ်ချက်ဖြစ်နေတယ်
                Amazon SNS	Pub/sub notifications, message fan-out	Subscribers အများအပြားဆီ message ပို့ဖို့ ကောင်းတယ်
                Elastic Load Balancing	Incoming traffic ကို targets အများအပြားဆီ ဖြန့်ဝေခြင်း	Application တွေကို asynchronous event bus အဖြစ် decouple မလုပ်ပေးဘူး
                EventBridge နဲ့ SQS ဘာကွာသလဲ?
                - EventBridge = ဘယ် event ကို ဘယ် target ဆီ ပို့မလဲဆိုတာ ဆုံးဖြတ်ပေးတယ်။
                - SQS = Message ကို queue ထဲမှာ သိမ်းထားပြီး consumer အဆင်သင့်ဖြစ်တဲ့အချိန် process လုပ်နိုင်စေတယ်။
                - SNS = Message တစ်ခုကို subscribers အများအပြားဆီ fan-out လုပ်ပေးတယ်။
                EventBridge နဲ့ SQS/SNS တို့ဟာ အစားထိုးသုံးရတဲ့ service တွေချည်း မဟုတ်ပါဘူး။ လိုအပ်ရင် EventBridge rule ရဲ့ target အဖြစ် SQS သို့မဟုတ် SNS ကိုပါ သုံးနိုင်ပါတယ်။
            3. Exam မှာ သတိထားရမယ့်အချက်
                မေးခွန်းထဲမှာ third-party SaaS application က events တွေ ထုတ်ပေးတယ် ဆိုတာက အရေးကြီးဆုံး clue ပါ။
                SaaS events + event rules + multiple targets
                → Amazon EventBridge

                Buffer messages + retry processing + smooth traffic spikes
                → Amazon SQS

                Broadcast notifications to many subscribers
                → Amazon SNS

                မှတ်ဉာဏ်လွယ်အောင်: SaaS events → EventBridge, Queue and retries → SQS, Pub/sub fan-out → SNS။

                သတိပြုရန် — EventBridge က event routing ကို asynchronous ပုံစံနဲ့ လုပ်ပေးနိုင်ပေမဲ့ delivery ကို အမြဲတမ်းချက်ချင်း သို့မဟုတ် 
                တစ်ကြိမ်တည်းသာ ဖြစ်မယ်လို့ မယူဆသင့်ပါဘူး။ 
                လိုအပ်တဲ့ reliability အတွက် retries, dead-letter queues (DLQs) နဲ့ idempotent processing တို့ကိုပါ စီစဉ်သင့်ပါတယ်။

        ECMP ဆိုတာဘာလဲ?
            ECMP (Equal Cost Multipath) ဆိုတာ cost တူညီတဲ့ network paths အများအပြားကို routing အတွက် အသုံးပြုနိုင်စေတဲ့ နည်းလမ်းပါ။
            ဥပမာ၊ VPN tunnel တစ်ခုချင်းစီက traffic အားလုံးကို တစ်ခုတည်းက သယ်ဆောင်ရမယ့်အစား ECMP က traffic flows အများအပြားကို 
            VPN paths အများအပြားပေါ် ခွဲဝေပို့နိုင်ပါတယ်။ ဒါကြောင့် စုစုပေါင်း throughput တိုးလာနိုင်ပါတယ်။

S3 Bucket Keys ဆိုတာ ဘာလဲ?
    ပုံမှန် SSE-KMS encryption မှာ S3 က object တစ်ခုချင်းစီအတွက် data key ရယူရာမှာ AWS KMS ကို မကြာခဏ request လုပ်ရနိုင်ပါတယ်။
    Object အရေအတွက်များပြီး upload များလာတဲ့အခါ KMS request cost တက်လာနိုင်ပါတယ်။
    S3 Bucket Keys ကို enable လုပ်လိုက်ရင် S3 က bucket-level key ကို အသုံးပြုပြီး KMS ဆီ တိုက်ရိုက်သွားရတဲ့ request အရေအတွက်ကို လျှော့ချနိုင်ပါတယ်။

Amazon Transcribe + Amazon Athena
    Audio to text → Amazon Transcribe
    Ad-hoc SQL queries on S3 → Amazon Athena
    Sentiment analysis → Amazon Comprehend သို့မဟုတ် အခြား NLP model
    Visual dashboards and reporting → Amazon QuickSight

    AWS service	Why it is correct or incorrect
    Amazon Transcribe: Correct for converting audio recordings into text.
    Amazon Athena: Correct for running ad-hoc SQL queries on data stored in S3. However, Athena does not automatically perform sentiment analysis. You need sentiment labels generated by Amazon Comprehend or another NLP solution.
    Amazon QuickSight: Incorrect as the primary answer because it is mainly used for dashboards and data visualization, rather than audio transcription or ad-hoc SQL querying.
    Amazon Kinesis Data Streams: Incorrect because it collects and streams real-time data; it does not transcribe audio by itself.
    Amazon Alexa: Incorrect because it is not the appropriate AWS analytics service for this architecture.
