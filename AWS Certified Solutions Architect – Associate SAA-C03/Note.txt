                        explanation:
                            One-Time vs Persistent Request

                            This is the most important part.

                            There are two request types.

                            ① One-Time Request

                            Imagine you tell AWS:

                            I need one Spot Instance.

                            AWS finds one.

                            Spot Request
                                │
                                ▼
                            Launch EC2

                            Later, the instance is interrupted or terminated.

                            What happens?

                            Nothing.

                            The request is finished.

                            AWS does NOT launch another EC2.

                            Example:

                            Request
                                │
                            Launch EC2
                                │
                            Interrupted
                                │
                            Finished
                            Myanmar

                            One-Time ဆိုတာ

                            တစ်ခါပဲ တောင်းတာ

                            Instance ပျက်သွားရင်

                            AWS က အသစ်ပြန်မဖန်တီးဘူး။
                            ② Persistent Request

                            Now imagine you tell AWS:

                            I always want one Spot Instance running.

                            AWS launches one.

                            Spot Request
                                │
                                ▼
                            EC2 Running

                            If AWS interrupts it:

                            EC2 Interrupted
                                │
                                ▼
                            AWS automatically tries
                            to launch another one

                            As soon as capacity becomes available, AWS starts a replacement.

                            Myanmar

                            Persistent ဆိုတာ

                            အမြဲတမ်း EC2 ရှိနေချင်တယ်။

                            တစ်လုံးပျက်သွားရင်

                            AWS က အသစ်တစ်လုံး
                            ထပ်ရှာပြီး run ပေးမယ်။

                            Step 3: Why Can't I Just Terminate the EC2?

                            Suppose you have:

                            Persistent Request
                                    │
                                    ▼
                            Spot EC2

                            You terminate the EC2 manually.

                            What happens?

                            AWS sees:

                            The request still exists!

                            So AWS launches another EC2.

                            Terminate EC2
                                │
                                ▼
                            AWS creates new EC2

                            Many beginners are surprised by this behavior.

                            To Stop Everything

                            You must:

                            Cancel the Spot Request
                            Then terminate the Spot Instance (if it's still running)

                            Otherwise AWS continues trying to satisfy the request.

                            Step 4: What Does This Mean?

                            Your note says:

                            You can only cancel spot instance requests that are open, active, disabled.

                            These are the request states.

                            Open

                            AWS is still looking for capacity.

                            Need EC2
                            Searching...

                            No instance yet.

                            Active

                            AWS found capacity.

                            Spot Request
                                │
                                ▼
                            EC2 Running
                            Disabled

                            The request exists, but AWS isn't launching instances right now.

                            Think of it as paused.

                            Only these request states can be cancelled.

                            If a request is already completed or cancelled, there's nothing left to cancel.

                            Real Example

                            Suppose you create:

                            Persistent Request

                            1 x t3.medium

                            AWS launches:

                            EC2 #1

                            AWS later interrupts it.

                            EC2 #1
                            Stopped

                            AWS automatically launches:

                            EC2 #2

                            You don't want any more Spot Instances.

                            Wrong way:

                            Terminate EC2 #2

                            AWS immediately launches:

                            EC2 #3

                            Correct way:

                            Cancel Persistent Request

                            Then
                            Terminate EC2
                            Now AWS stops creating new instances.

        Private vs Public IP (IPv4) Fundamental Differences
            Public IP:
                Public IP means the machine can be identified on the internet (WWW) 
                    Public IP ဆိုတာ Internet ပေါ်ကနေ တိုက်ရိုက်ရှာတွေ့နိုင်တဲ့ IP 
                Must be unique across the whole web (not two machines can have the same public IP).
                Can be geo-located easily
            Private IP:
                Private IP means the machine can only be identified on a private network only
                    Private Network အတွင်းမှာပဲ အသုံးပြုတဲ့ IP
                The IP must be unique across the private network
                BUT two different private networks (two companies) can have the same IPs.
                    Because they are different private networks. They never see each other.
                Machines connect to WWW using a NAT + internet gateway (a proxy)
                    using flow:
                        Private EC2
                            │
                            ▼
                        NAT Gateway
                            │
                            ▼
                        Internet Gateway
                            │
                            ▼
                        Internet
                        Imagine:
                            Private EC2
                            10.0.1.10

                            It wants to install updates.

                            Destination: ubuntu.com

                            But

                            10.0.1.10
                            is private.

                            Internet doesn't know where it is.
                        NAT means: Network Address Translation
                            It changes:
                            Private IP
                            ↓
                            Public IP
                        Example
                            Before NAT
                            10.0.1.10

                            After NAT
                            54.12.90.8

                            Internet sees:
                            54.12.90.8

                            not
                            10.0.1.10
                        Without NAT
                            Private EC2
                            10.0.1.10
                            ↓
                            Internet
                            ❌ Doesn't know this IP
                        Important:
                            A Private EC2 can:
                            ✅ Access Internet (through NAT Gateway)

                            But
                            ❌ Internet cannot start a connection to the Private EC2.

                            This is why private subnets are much more secure.

        First, Why Do We Need Placement Groups?
            Normally, when you launch EC2 instances:

            EC2-1
            EC2-2
            EC2-3

            AWS decides where to place them.

            You don't control:

            Which physical server
            Which rack
            How close they are

            AWS automatically chooses.

            Sometimes, however, you have special requirements.

            For example:

            Requirement 1
            I want all EC2s
            to communicate
            VERY FAST.

            OR

            Requirement 2
            I don't want
            all EC2s to fail
            at the same time.

            AWS asks:

            "How should I place your EC2 instances?"

            That's exactly what Placement Groups are for.
        သတ်မှတ်ပေးတဲ့ Strategy: 3
            Cluster Placement Group
                Keyword: Performance
                aws pusts ec2: Very close together. communication becomes extremely fast.
                EC2 တွေကို
                တစ်နေရာတည်း
                အနီးနားမှာထားတာ။
                Disadvantage:
                    Imagine Rack A catches fire.
                    Everything fails together.
                    Higher performance,
                    Lower fault tolerance (အမှားခံနိုင်ရည်နည်းခြင်း)
                Note: Very safe.
            Spread Placement Group
                Keyword: Availability
                aws pusts ec2: separates EC2 instances.
                EC2 တွေကို
                တစ်နေရာတည်းမှာ မထားဘူး။
                ဝေးဝေးခွဲထားတယ်။
                Note: very safe.
            Partition Placement Group
                Each partition uses completely different racks.
                Partition Placement Group ဆိုတာ
                EC2 တွေကို
                အုပ်စုကြီးတွေခွဲထားတာ။
                Many Instances
                ↓
                One Partition
                Applications like:
                Hadoop, HDFS, HBase,
                Apache Kafka
                Cassandra,
                Hundreds of EC2
                already work in partitions.
                AWS aligns the hardware with the application design.
                Note: Scalable + fault isolation(ချို့ယွင်းချက်ခွဲထုတ်ခြင်း။)
            Memory:
                | Strategy      | Goal                               | Best For                    | Risk                                       | 
                | ------------- | ---------------------------------- | --------------------------- | ------------------------------------------ |
                | **Cluster**   | Lowest latency                     | HPC, ML, Trading            | One rack failure can affect many instances |
                | **Spread**    | Highest availability               | Critical applications       | Max 7 instances per AZ                     |
                | **Partition** | Fault isolation for large clusters | Hadoop, Cassandra, Kafka,Big Data| One partition can fail, others continue    |
                HPC means high-performance computing.

    Hibernate:
        3 important (lifecycle)actions:
            1. Stop
                After Stop
                    RAM
                    -------------
                    ❌ Cleared

                    EBS
                    -------------
                    ✅ Still Exists
                When Start again
                    AWS does:
                    Boot Operating System
                    ↓
                    Start Services
                    ↓
                    Start Application

                    Everything starts from the beginning.
                If EC2 is stopped,
                RAM is cleared.
                Redis cache disappears (unless configured otherwise).
                When EC2 starts,
                it must rebuild the cache. caches get warmed up, and that can take time!
                This causes slower startup.
                    Cache Warm-up:
                        our application uses Redis.
                            Initially

                            Cache

                            Empty

                            First user visits.

                            Database
                            ↓
                            Redis

                            Now cache becomes populated.
                            This is called Cache Warm-up.
            2. Hibernate
                Think of Windows.
                Instead of Shut Down,
                you click:
                Hibernate
                Computer powers off.
                BUT
                before shutting down,
                Windows saves RAM to disk.
                AWS does exactly the same.
                Before Hibernate
                    RAM
                        Application
                        Browser
                        Variables
                        Sessions
                    AWS copies RAM -> EBS
                    Then powers off.
                    When Start again
                        AWS does
                        Read RAM
                        ↓
                        Restore Memory
                        ↓
                        Continue
                        Application continues exactly where it stopped.
                Why is Hibernate faster?
                    Because OS is not stopped / restarted, aws perform: OS -> frozen(Pause) instead of shutdown.
                    Normal Start
                        Boot OS
                        ↓
                        Start Application
                        ↓
                        Load Cache
                        ↓
                        Reconnect DB
                        ↓
                        Ready
                        Maybe 60 seconds
                    Hibernate
                        Power On
                        ↓
                        Restore RAM
                        ↓
                        Continue
                        Maybe 15 seconds
                Is our application still running?
                    No.
                    Power is OFF.
                    CPU is OFF.
                    RAM has no power.
                    Nothing is executing.
                Why must Root EBS be encrypted?
                    Root EBS is the boot disk.
                        Imagine RAM contains
                            Password
                            API Keys
                            JWT Token
                            Database Password
                            User Session
                        AWS saves RAM
                        ↓
                        EBS

                        If EBS wasn't encrypted
                        someone with disk access could potentially read all those secrets.
            3. Terminate
                Terminate means
                    Destroy. RAM and Root EBS Deleted. Everything is gone.
        Compare All Three:
            Stop
                RAM ❌ Lost
                EBS ✅ Keep
            Hibernate
                RAM ✅ Saved (preserved=မပျောက်အောင် သိမ်းထားတာ)
                EBS ✅ Keep
            Terminate
                RAM ❌ Lost
                EBS ❌ Lost

            many beginners think: "All EC2 storage = EBS"
                ❌ Not true.

                1. EBS (Network Storage)
                2. Instance Store (Physical Storage)
            • EBS volumes are network drives with good but "limited" performance
            • If you need a high-performance hardware disk, use EC2 Instance Store.
                Because: The disk is physically attached to the host machine.
                example:

                        Your PC
                            ↓
                            Network
                            ↓
                            Storage
                        Because it is over the network:
                        Some latency exists.

                        Your PC
                        ↓

                or

                or

                Need maximum speed.

                    EBS
                    Stop EC2
                    ↓
                    Data Survives

                    Instance Store
                    Stop EC2
                    ↓
                    Data Lost

                For EBS:
                    Snapshot
                    AWS helps.

                For Instance Store:
                    You handle backup
                    Your application must replicate data elsewhere.

        Termination policy:
            If desired decrease/Scale-In, How to choose termination of instance?
                AWS does not simply terminate the newest (latest) instance first.
                AWS follows a termination policy.
                Termination policy:
                    priorities:
                        Keep Availability Zones balanced.
                        Prefer terminating instances that use older launch templates/configurations.
                        Then apply the configured termination policy (which may consider launch time).
                    explanation:
                        Step 1: Is one AZ holding more instances?

                            Example:

                            AZ-A

                            3 instances
                            AZ-B

                            1 instance

                            AWS prefers to terminate an instance from AZ-A to keep the AZs balanced.

                            This helps maintain High Availability.
                        Step 2: Which Instance Should Be Removed?

                            If there are multiple candidates, AWS looks at the termination policy.

                            The default policy generally prefers to terminate instances launched from older launch configurations/templates or mixed-instance configurations first, before considering launch time.

                            If all instances are equivalent, launch time may become one of the deciding factors.

                            Example

                            Suppose:

                            10:00

                            EC2-A
                            10:05

                            EC2-B
                            10:10

                            EC2-C
                            10:15

                            EC2-D

                            If all four are:

                            Same Launch Template
                            Same AZ balance
                            Same configuration

                            Then AWS may terminate one of the newer instances according to its default policy.

                            But don't memorize "latest is always deleted." That is not the rule.

                            Why?

                            Imagine:

                            Old instances:

                            Launch Template v1

                            New instances:

                            Launch Template v2

                            You update your application.

                            AWS would rather keep:

                            v2

                            and remove:

                            v1

                            because v2 contains the latest software.

    Routing Policy:
        Route53 must decide which answer to return.
        Route53 never sends traffic.
            Route53 က Traffic ကို လမ်းမညွှန်ဘူး။
            သူလုပ်တာက "ဒီ Domain အတွက်
            ဘယ် IP ကို သွားရမလဲ?" ဆိုတဲ့ Question ကို ဖြေပေးတာပဲ။
            ပြီးရင် Browser က IP ကို တိုက်ရိုက်သွားတယ်။
        different decision rules:
            Simple Routing:
                Always return one resource.
                ဘာမှ မစဉ်းစားဘူး။
                User မေးရင် Record ထဲမှာ ရှိတာကို
                ပြန်ပေးလိုက်တာပဲ။
                eg:
                    www.myshop.com
                    ↓
                    18.100.20.30
                    No intelligence.
                    No failover.
                    No weighting.
                Can specify multiple values in the same record.
                    If multiple values are returned, a random one is chosen by the client.
                    Is this Load Balancing?
                    Many beginners think
                    "Wow, that's Load Balancing."
                    ❌ Not really.
                    Because
                        No health check
                        No traffic percentage
                        No intelligent routing

                    It's just
                    multiple IPs.
                    The client decides.
                When Alias enabled, specify only one AWS resource.
                cannot be associated with Health Checks.
            Weighted Routing:
                Instead of
                    Every user goes to Server A
                You can say
                    70% → Server A
                    30% → Server B
                Return records based on percentage.
                    traffic(%) = weight for a specific record/sum of all weights for all records.
                    Weights don't need to sum up to 100.
                    Any numbers are okay. AWS only cares about the ratio.
                DNS records must have same name and type(A/AAAA,etc).
                Can be associated with Health Checks.
                If all records have weight 0, Everyone(server) becomes equal.
                Traffic ကို ရာခိုင်နှုန်းအလိုက် ခွဲပေးတာ

    Health Checks:
        Health Check ဆိုတာ Route53 က Server ကို အမြဲစစ်နေတဲ့ Doctor လိုပါပဲ။
        are only for public resources. 
            Route53 Health Checker က Internet ပေါ်ကလာတာပါ။ ဒါကြောင့် Public IP ရှိတဲ့ Server ကိုပဲ စစ်နိုင်တယ်။
            Health Checkers are AWS services running outside your VPC. 
            They need to access your endpoint through the Internet.
            e.g: if Private EC2, internet to Private EC2 is Impossible because no public IP.
        CloudWatch Alarm Health Check
            health check use cloudwatch, it cannot be checked directly to Private RDS.
                because CloudWatch already monitors CPU, Free Storage, Connections, metrics.
        Calculated Health Checks
            Instead of checking a server, Route53 check other health checks.
                e.g:
                    Health Check A => Healthy
                    Health Check B => Healthy
                    Health Check C => Dead
                    ↓
                    Calculated Health Check
                    ↓
                    Healthy
            combine the results of multiple health checks into a single Health check.
            we can use OR, AND or NOT(Reverse the result).
                real world example:
                    Suppose
                        you own: shop.com
                        Website needs
                        3 services.
                            Web Server
                            API Server
                            Database Proxy

                        Each has Health Check.

                        If all must work
                        ↓
                        Use AND.

                        Visual:
                            Web => Healthy
                            API => Healthy
                            DB => Healthy
                            ↓
                            Website => Healthy.

                            If API fails
                            ↓
                            Website => Fail.
                NOT(Reverse the result):
                    Server က မပျက်ဘူး။ ဒါပေမယ့် Maintenance Mode ဝင်နေတယ်။
                    User က အသုံးမပြုနိုင်ဘူး။
                    ဒါကြောင့် Healthy ဖြစ်နေပေမယ့် Business အတွက် Unhealthy ဖြစ်ချင်တယ်။
                    အဲဒီအချိန် NOT အသုံးဝင်တယ်။
            can monitor up to 256 Child Health Checks.
            perform maintenance without causing all health checks to fail.
            ဥပမာ 
                Server ၂ လုံးရှိတယ်။ Server A ကို Upgrade လုပ်မယ်။ Upgrade လုပ်နေချိန် Health Check Fail ဖြစ်မယ်။
                ဒါပေမယ့် Server B ကောင်းနေသေးတယ်။
                Calculated Health Check မှာ At least 1 လို့ထားရင် Website တစ်ခုလုံး Healthy လို့ပဲ သတ်မှတ်နေမယ်။
                User တွေ Website ကို ဆက်သုံးလို့ရတယ်။

            Every Health Check produces CloudWatch Metrics.
            in CloudWatch Dashboard, we can see Healthy, Unhealthy, Response Time, Failures.

            15 global health checkers will check the endpoint health

    Geoproximity Routing:
        If we have two server, aws draw a boundary on between.
        Unlike Geolocation, AWS lets you manually change each server's geographic influence.
            Geoproximity Routing ဆိုတာ User နဲ့ Serverဘယ်သူက
            မြေပုံအရ ပိုနီးလဲဆိုတာကိုကြည့်ပြီးရွေးပေးတာ။
            ဒါပေမယ့် Boundary ကို ကိုယ်တိုင် ပြောင်းလို့ရတယ်။
            ဒါက Geolocation နဲ့ မတူတဲ့အချက်ပါ။
        What is Bias?
            AWS lets you say
                I want Tokyo to serve more users.
                or
                I want Singapore to serve fewer users.

                This is called Bias.
            Positive Bias (+):
                expand(1 to 99), more traffic, larger boundary, more user will get.
                Coverage Area ကို ချဲ့လိုက်တာ။ ပိုများတဲ့ User တွေသွားမယ်။
            Negative Bias (-):
                Shrink (-1 to -99), less traffic,
                Coverage ကို ကျုံ့လိုက်တာ။ ဒါကြောင့် User နည်းသွားမယ်။
        Non-AWS Resources:
            if we own DataCenter, AWS cannot know Geolocation, So need to set Latitude and longitude.
        Why use Geoproximity?
            Suppose
                Tokyo Server is expensive.

                Singapore is cheaper.

                You want more users to go Singapore.

                Set: Singapore => Bias +60

                Singapore serves more users.
        Traffic Flow:
            Must use Route53 Traffic Flow.
            Geoproximity Routing ကို
            Route53 Console မှာ Simple, Weighted, Latency, Geolocation toe lo
            Record တစ်ခုထည့်သလို မလုပ်နိုင်ဘူး။
            Route 53 Traffic Flow ဆိုတဲ့ Advanced Feature ကို သုံးရပါတယ်။

        Based on user's IP address (CIDR)
            More control than Geolocation.
            Useful when users from the same country should be routed differently.
            Can optimize traffic for known ISP networks.
    Multi-Value Routing:
        maximum return: 8 healthy records although 20 healthy server.
        Multi-Value is not a substitute for having an ELB
            Not Like ELB:
                Route53 က IP Address တွေ ပြန်ပေးရုံပဲ။ 
                ဘယ် Server ကို တကယ်သွားမလဲဆိုတာ Client (Browser / OS)က ဆုံးဖြတ်တာ။
                AWS က မထိန်းချုပ်ဘူး။
            ELB: 
                The Load Balancer makes the decision.
                It continuously monitors the servers and distributes requests.
                Request တစ်ခုချင်းစီကို Load Balancer ကိုယ်တိုင် Server ရွေးပေးတာ။

            Good for
                Small websites
                Simple redundancy
                Multiple EC2 instances
                Basic availability
            Not good for
                Thousands of requests
                Sticky Sessions
                WebSockets
                Path-based routing
                Cookie-based routing
                Advanced load balancing.

            Networks can be:
                VPC itself / Peered VPC
                On-premises Network (connected through

            Why VPN or Direct Connect?
                AWS cannot directly access your office.
                Need a network connection.
                Usually
                    Site-to-Site VPN
                    or
                    AWS Direct Connect
            Note:
                Hybrid means
                    Two different environments working together.
            Inbound Endpoint:
                Used when on-premises DNS servers need to resolve AWS private DNS names.
                Requires:
                    VPN or Direct Connect
                    Security Group allowing UDP/TCP port 53
                    Endpoints deployed in at least two subnets/AZs for high availability
                What is an Inbound Endpoint?
                    Allows your on-premises DNS resolver to resolve DNS records inside AWS.
                    Or simply:
                    Outside → AWS
                Inbound Endpoint ဆိုတာ အပြင် (On-Premises) ကနေ AWS ထဲက Private Hosted Zone EC2 Hostnameတို့ကို
                    လာမေးနိုင်အောင် လုပ်ပေးတဲ့ "DNS Door"ဖြစ်ပါတယ်။
                Inbound means: into AWS
                flow:
                    Office DNS
                    asks
                    Inbound Endpoint
                    Inbound Endpoint asks
                    Route53 Resolver
                    Route53 Resolver replies
                    10.0.2.50
                    Office receives
                    the answer.
                Why can't Office contact Route53 Resolver directly?
                    Route53 Resolver is managed internally by AWS. It has no public interface.
                    AWS exposes special ENIs(Elastic Network Interfaces) called Inbound.
                High availability:
                    When creating
                        an Inbound Endpoint
                        AWS asks
                        for
                            Subnet A
                            Subnet B
                    Why?
                        High Availability.
                        If one AZ dies, the other still answers DNS queries.
                Security Group:
                    Inbound Endpoint is inside of VPC, SG must allow DNS traffic.
            Outbound Endpoint:
                AWS ---> Outside
                Allows Route 53 Resolver to forward DNS queries from AWS to your on-premises DNS server.
                AWS ထဲက EC2, Lambda စတဲ့ Resources တွေက
                On-Premises DNS ကို မေးချင်တဲ့အခါ အသုံးပြုတဲ့ DNS Door ဖြစ်ပါတယ်။
                Flow:
                    Suppose EC2 runs
                        ping printer.office.local
                        Step 1
                            EC2
                            ↓
                            Route53 Resolver
                        Step 2
                            Resolver says

                            "I don't know."

                            But

                            there is

                            a forwarding rule.
                            ↓
                            Forward to

                            Outbound Endpoint
                        Step 3
                            Outbound Endpoint

                            sends

                            the query

                            over VPN.
                            ↓
                            Office DNS.
                        Step 4
                            Office DNS replies

                            192.168.1.50
                        Step 5
                            EC2 gets the answer.
                            Done.
                    Why do we need Forwarding Rules?
                        Outbound Endpoint
                        does NOT automatically know
                        which domains should go to Office.
                        You must create a forwarding rule.
                        e.g:
                            Example
                                office.local
                                ↓
                                Forward to

                                192.168.1.10

                                Now

                                Every time

                                AWS sees

                                *.office.local
                                ↓
                                Forward

                                to

                                Office DNS.
                    Why not just use Public DNS?
                    Security Group:
                        lives inside your VPC. allow UDP 53, TCP 53
                    Two Subnets:
                        for High Availability.
            Important:
                Ask yourself:
                    "Who is asking the DNS question?"

                If the question comes from
                    On-Premises → Inbound Endpoint
                    AWS (EC2/Lambda/etc.) → Outbound Endpoint

s3:
    one of main building blocks of AWS.
    infinitely scaling storage.
    many websites use Amazon S3 as backbone.
    for backup and storage.
    disaster recovery, archive, Hybrid cloud storage, application storage, 
    media hosting, data lakes & big data analysic
    software delivery, static website
    Buckets:
        directories to store objects(files)
        region level. s3 look like a global service but, buckets are created in a region.
        Naming:
            shared global namespace: globally unique name. Nobody cannot create same.
            account regional namespace: allows for reuse of same bucket name across regions
        Naming constraints:
            no uppercase, no underscore.
            not an ip, must start with lowercase or number.
            must not start with a prefix xn--
            must not end with a suffix minus -s3alias.
    Objects:
        have a Key.
        Key is everything after the bucket name.
            eg: s3://my-bucket/my_file.txt.
                part of [my_file.txt.] is Key.
            eg: s3://my-bucket/my_folder/another_folder/my_file.txt.
                part of [my_folder/another_folder/my_file.txt.] is Key.
        composed of prefix + object name.
            eg: s3://my-bucket/my_folder/another_folder/my_file.txt.
                part of [my_folder/another_folder/] is prefix.
                part of [my_file.txt] is object name.
        no concept of 'directories' within buckets.
            Why do I see folders?
            Actually
                There are no real folders.
                S3 only stores one string.
                The / is just a character. AWS Console pretends it is a folder 
                    to make it easier for humans.
        Max: 50 TB.
            if >50 GB, must use 'multi-part upload'
        Metadata:
            list of text key/value pairs.
        Tags:
            unicode key/value pair
        Version ID: if versioning is enabled.
    Security:
        User-Based:
            IAM Policies:
                လူကို Permission ပေးတာ
                which API calls should be allowed for a specifc user from IAM.
        Resource-Based:
            Bucket Policies:
                Permission ကို Bucket မှာရေးတာ ဖြစ်တယ်။
                more used.
                bucket wide rules from the s3 console - allows cross account.
                structure:
                    {
                        "Version": "2012-10-17",
                        "Statement": [
                            {
                                "Effect": "Allow",
                                "Principal": "...",
                                "Action": "...",
                                "Resource": "..."
                            }
                        ]
                    }
                    Resource: Which bucket or object does this policy apply to?
                        All objects inside the bucket. eg: arn:aws:s3:::study-files/*
                    Effect: Allow or Deny.
                    Action: Which S3 API operations are allowed?
                    Principal: Who gets this permission?
                        One AWS account: 
                            "Principal": {
                                "AWS": "arn:aws:iam::111122223333:root"
                            }
                        Everyone:
                            "Principal": "*"
                        Usecase:
                            Cross-Account Access:
                                Company A owns the bucket.
                                Company B needs to upload files.
                                Instead of creating IAM users in Company A,
                                Bucket Policy says:
                                Principal
                                ↓
                                Company B Account

                                Now Company B can access.
                            Only One IAM User:
                                Principal
                                    ↓
                                    John
                    Policy Generator:
                        https://awspolicygen.s3.amazonaws.com/policygen.html
            Object Access Control list(ACL):
                Object-level special permissions
                older feature, rarely used.
                    AWS recommends Disable ACLs and use Bucket Policy.
            Bucket Access Control list(ACL):
                less common (can be disabled)
            Bucket settings for Block Public Access:
                created to prevent company data leaks. safety switch.
                    Even if the Bucket Policy says:
                    Allow everyone
                    Block Public Access says:
                    ❌ Ignore that. Keep the bucket private.
        Note:
            AWS checks
                IAM Policy OR Bucket Policy If either allows -> Access.
                BUT there is another rule.
                Someone is DENY, result -> Deny.
                AWS က Permission စစ်တဲ့အချိန်
                    ဒီလိုစဉ်းစားတယ်။
                    IAM မှာ Allow ရှိလား?
                    ဒါမှမဟုတ်
                    Bucket Policy မှာ Allow ရှိလား?
                    တစ်ခုခုမှာ Allow ရှိရင် ဝင်လို့ရတယ်။
                    ဒါပေမယ့် တစ်နေရာရာမှာ Deny ရှိသွားရင် အားလုံးကို ပယ်လိုက်တယ်။
                    ဒါကို AWS မှာ Explicit Deny Overrides Allow
            If there is NO Allow anywhere, the result is DENY.
                AWS has two types of deny:
                    Implicit Deny (default) ← very common
                    Explicit Deny ← overrides everything
                    | IAM Policy | Bucket Policy | Result  | Reason                      |
                    | ---------- | ------------- | ------- | --------------------------- |
                    | Nothing    | Nothing       | ❌ DENY  | Implicit Deny (default)     |
                    | Allow      | Nothing       | ✅ ALLOW | IAM grants access           |
                    | Nothing    | Allow         | ✅ ALLOW | Bucket Policy grants access |
                    | Allow      | Allow         | ✅ ALLOW | Either Allow is sufficient  |
                    | Allow      | Deny          | ❌ DENY  | Explicit Deny overrides     |
                    | Deny       | Allow         | ❌ DENY  | Explicit Deny overrides     |
                    | Deny       | Deny          | ❌ DENY  | Explicit Deny               |
            Final Access = (IAM Allow OR Bucket Policy Allow)
                            AND
                            No Explicit Deny
            | Security Method | Attached To         | Typical Use                                            |
            | --------------- | ------------------- | ------------------------------------------------------ |
            | IAM Policy      | User / Group / Role | Control what identities in your account can do         |
            | Bucket Policy   | Bucket              | Cross-account access, public access, bucket-wide rules |
            | Object ACL      | Individual object   | Legacy, fine-grained object permissions                |
            | Bucket ACL      | Bucket              | Legacy, rarely used

        Replication means:
            Automatically copy objects from one S3 bucket to another.

                    Upload File
                    ↓
                    Upload Success ✅
                    ↓
                    (Background)
                    ↓
                    Replicate to Singapore
                    Your upload finishes immediately.
                    Replication happens later in the background.

            Source Bucket in account A => Destination Bucket in account B.

            Only new objects uploaded after replication is enabled are replicated.
                Replication ဖွင့်ပြီးမှ အသစ် Upload လုပ်တဲ့ File တွေကိုပဲ AWS က Copy လုပ်ပေးတယ်။
                Replication မဖွင့်ခင်က ရှိပြီးသား File တွေကို အလိုအလျောက် မကူးဘူး။

                S3 Batch Replication:
                    Replicate everything that already exists.
                S3 Batch Replication also retries failures:
                    Suppose
                        photo1.jpg
                        failed to replicate yesterday.
                        You can ru S3 Batch Replication
                        again.
                        AWS will retry those failed objects.

                | Object Type         | Normal Replication | Batch Replication |
                | ------------------- | ------------------ | ----------------- |
                | New Objects         | ✅ Yes              | ✅ Yes             |
                | Existing Objects    | ❌ No               | ✅ Yes             |
                | Failed Replications | ❌ No               | ✅ Yes             |
        DELETE Operations:
            Some companies want:
                Delete in Production
                ↓
                Delete in Backup
            Others want:
                Delete in Production
                ↓
                Keep Backup
            AWS lets you choose.
            AWS intentionally does not replicate version-specific deletes.
                AWS က Backup ကို ကာကွယ်ချင်တယ်။
                တစ်ယောက်ယောက်က Source Bucket မှာ Version ID နဲ့ Permanent Delete လုပ်လိုက်ရင်
                Destination Bucket ကို မလိုက်ဖျက်ဘူး။ ဒီလိုမှ Backup Copy ကျန်မယ်။
            | Delete Type                       | Replicated? |
            | --------------------------------- | ----------- |
            | Delete Marker                     | ✅ Optional  |
            | Permanent Delete using Version ID | ❌ No        |
        Chaining Replication:
            Replication is not transitive (no chaining).
            AWS intentionally avoids replication loops.
            Suppose
                Bucket A
                ↓
                Replicate
                ↓
                Bucket B
                ↓
                Replicate
                ↓
                Bucket C

                Question: Upload to Bucket A.
                Will it automatically reach Bucket C?
                    If after B -> stops -> doesnot continue to Bucket C.
                AWS intentionally avoids replication loops.
                    Imagine
                        A → B
                        B → C
                        C → A

                        Without this protection:
                        A
                        ↓
                        B
                        ↓
                        C
                        ↓
                        A
                        ↓
                        B
                        ↓
                        C

                        ∞

                        Infinite replication!
                        AWS prevents this.

        4 methods:
            SSE(Server side encryption):
                SSE-S3:
                    default, keys handled, managed, owned by AWS. AWS does everything.
                    type: AES-256
                    must set header: "x-amz-server-side-encryption":"AES256"
                    enabled by default for new buckets & new object

                    keys handled, managed, owned by AWS KMS.

                    must set header: "x-amz-server-side-encryption":"aws:kms"

                        Every download use:
                            Decrypt KMS API.

                SSE-C:
                    S3 never stores your key.
                    manage by own key. fully managed by customer.
                        If you lose the key:
                            Data is gone.
                        AWS cannot recover it.
                    HTTPS must be used.
                    key must provided in HTTPS headers, for every HTTP request made.

                        Upload (PUT):
                            Your File
                                +
                            Your Encryption Key
                                ↓
                            HTTPS
                                ↓
                            S3 encrypts the file
                                ↓
                            Stores only the encrypted object
                                ↓
                            Discards your key

                            Encrypted Object
                                +
                            You send the SAME key again
                                ↓
                            HTTPS
                                ↓
                            S3 decrypts temporarily
                                ↓
                            Returns plaintext to you
                                ↓
                            Discards the key again

    CORS:
        Cross-Origin Resource Sharing:
            Origin = Protocol + Domain + Port
                Example:
                    https://www.example.com
                    means
                        Protocol: HTTPS
                        Host:     www.example.com
                        Port:     443 (default)
                Another example:
                    http://www.example.com:8080

                    Origin is
                        Protocol: HTTP
                        Host: www.example.com
                        Port: 8080
                So, If any Protocol or Domain or Port are different, origin are different.
                So browsers have the: Same-Origin Policy.
                    Same-Origin Policy (SOP) enabled by default.
                    Same-Origin Policy (SOP):
                    The rule:
                        JavaScript from one origin cannot freely read data from another origin.
                        if difference origin => blocked.
                Without CORS:
                    if difference origin => blocked.
                With CORS enabled:
                    if difference origin => allowed.
                    Suppose:
                        Frontend: https://mywebsite.com

                        Images stored in: https://my-images.s3.amazonaws.com

                        User opens: https://mywebsite.com

                        JavaScript requests: https://my-images.s3.amazonaws.com/photo.jpg

                        Browser sees:
                            Origin A
                            ↓
                            Origin B
                            ↓
                            Different Origin

                        Without CORS: Blocked
                    CORS Configuration:
                        [
                            {
                                "AllowedOrigins": [
                                "https://mywebsite.com"
                                ],
                                "AllowedMethods": [
                                "GET"
                                ]
                            }
                        ]
                    Now S3 responds:
                        Access-Control-Allow-Origin: https://mywebsite.com

                        Browser says: OK
                        Allowed
                        Show image.
                Important:
                    Many beginners think:
                        S3 blocks the request.
                        Actually:
                        The request usually reaches S3.

                        It is the browser that blocks JavaScript from accessing the response 
                        if the required CORS headers are missing.
                Real-World Example
                    Your React application:
                    https://app.company.com

                    Uploads images to:

                    https://mybucket.s3.amazonaws.com

                    Need CORS.

    Object Lock:
        S3 Object တစ်ခုချင်းစီကို သတ်မှတ်ထားတဲ့အချိန်အတွင်း ဖျက်မရ၊ ပြင်မရအောင် lock လုပ်ခြင်း။
        Adopt a WORM (Write Once Read Many) model
        for special object only, not bucket level.
            Individual object version protection
        Retention mode:
            two Object Lock modes:
                Governance Mode:
                    normal user cannot delete, but, special user with s3:BypassGovernanceRetention can delete.
                Compliance Mode:
                    Object versions can't be overwritten or deleted by any user.
                        including root user.
                    Object retention modes can't be changed, and 
                        retention periods can't be shortened.
                            e.g: 10 years to 1 yr. result: Denied.
        Rentention Period:
            protect object for fixed period, can be extended.
                2 yrs => 5 yrs : can extend.
                5 yrs => 1 yr : violate WORM protection.
        Legal Hold:
            no expiration date.
            locked forever until removed.
            until someone manually removes the legal hold.
            Removing Legal Hold:

AWS DataSync:
    a high-speed data migration and synchronization service.
        think: moving truck for large amounts of data.
    Main purpose = Move LARGE amounts of data
    Important
        Outside AWS → AWS
            ↓
        Agent needed

        AWS → AWS
            ↓
        No agent
    Agent = software/appliance that you deploy close to your on-premises data source.
    Scheduled replication
        DataSync ကို တစ်ခါပဲ migration လုပ်တာမဟုတ်ဘဲ schedule ထားပြီး data ကို ထပ်ခါထပ်ခါ synchronize လုပ်နိုင်တယ်။
    File permissions and metadata are preserved

        ဘယ်သူပိုင်လဲ၊ group ဘာလဲ၊ permission ဘယ်လိုလဲ စတဲ့ file metadata/permissions တွေကို preserve လုပ်နိုင်တယ်။
    One agent task can use 10 Gbps
        but, you can configure Bandwidth limit.

                1 Gbps
                But DataSync tries to use too much bandwidth.

                    DataSync 🚀🚀🚀
                        ↓
                    Office Internet
                        ↓
                    Other applications ❌

                So you can limit the bandwidth DataSync uses.

                    DataSync
                    ↓
                    Bandwidth limit = X
                    ↓

    Big Different:
        Transfer Family => "I need FTP/SFTP."
            Typical use:
                External partners
                File exchange
                FTP/FTPS/SFTP
                CRM/ERP file transfers
        DataSync => "I need to move a HUGE amount of data."
            Typical use:
                Data migration
                Large-scale transfer
                Data synchronization
                Recurring replication
        DataSync vs Transfer Family vs Storage Gateway
            📂 "Users/partners transfer files using FTP/SFTP"
                        ↓
                TRANSFER FAMILY

            🚚 "Move/sync a huge amount of data"
                        ↓
                    DATASYNC

            💽 "On-premises application needs AWS-backed storage"
                        ↓
                STORAGE GATEWAY
            Transfer Family → File ပို့/ယူဖို့ FTP/SFTP
            DataSync → Data အများကြီးကို ရွှေ့/Sync လုပ်ဖို့

Storage Comparison:

    FSx for OpenZFS: Managed ZFS file system

Decoupling Application:
    when deploying multiple applications, they will inevitably need to communicate with one another.
        inevitably = မလွဲမသွေ
    two patterns:
        synchronous communications:
            eg: buying service => shipping service(directly connect)
            when a sudden spike of purchases or whatever,
                synchronous between applications can be a little bit problematic sometimes
                it's better to decouple your applications.
        asnchronous/Event Based communications:
            eg: buying service => queue => shipping service(not directly connect, queue in between)
            To decouple applications:
                using SQS: queue model.
                using SNS: pub/sub model.
                using Kinesis: real-time streaming model.
    SQS:
        Amazon Simple Queue Service
        Queue:
            is like a waiting line.
            The person who comes first is normally served first.
            FIFO = First In, First Out
        whatever msg go into the queue,
        consumers will poll the messages from the queue.
        Producer:
            The application that sends messages to the queue.
            Producing Messages:
                app => AWS SDK's SendMessage API -> SQS queue
                The message is persisted in SQS until a consumer deletes it
                    Producer က message ပို့ပြီးသွားတာနဲ့ ချက်ချင်းပျောက်မသွားဘူး။
                    Consumer က message ကို receive လုပ်ပြီး process လုပ်ပြီးတဲ့အခါ DeleteMessage လုပ်ရတယ်။
                    Consumer က message ကို delete မလုပ်သေးရင် SQS က retention period အတွင်း message ကို သိမ်းထားနိုင်တယ်။
        Consumer:
            The application that reads/processes messages from the queue.
            Consuming Messages:
                Consumer = Queue ထဲက message ကိုယူပြီး အလုပ်လုပ်ပေးတဲ့ application.
                Consumers can be EC2, servers, Lambda...
                consumer's job: 
                    SQS ထဲမှာ message ရှိလား? ရှိရင် ယူပြီး process လုပ်မယ်.
                Poll SQS for message:
                    Poll = "message ရှိလား?" လို့ SQS ကို သွားမေးတာ။
                Receive up to 10 messages at a time.
                    for Efficiency, တစ်ခါ polling လုပ်တဲ့အခါ up to 10 messages ရယူနိုင်တယ်။
                Process the messages
                    Message ကိုရပြီဆိုရင် application က actual work လုပ်တယ်။
                Receive လုပ်တာနဲ့ Delete မဖြစ်ဘူး
                    permanent delete မလုပ်သေးဘူး။
                    အဲဒီအချိန်မှာ SQS ရဲ့ Visibility Timeout
                    ဥပမာ Consumer က message ကိုယူပြီး process လုပ်နေတုန်း crash ဖြစ်သွားတယ်။
                        SQS
                        ↓
                        Consumer
                        ↓
                        💥 EC2 crashes

                        Message ကို Delete မလုပ်ရသေးဘူး။
                        ဒါကြောင့် SQS က message ကို နောက်ပိုင်းမှာ ပြန်ပေးနိုင်တယ်။
                        The golden rule:
                            Receive → Process → Delete
                        Process မအောင်မြင်သေးရင် Delete မလုပ်သင့်ဘူး။
        Flow:
            Producer → SQS Queue → Consumer
        Visibility Timeout:
            after receive msg on consumer, SQS doesn't immediately permanently delete it.
            Instead, the message becomes temporarily invisible to consumers.
            called Visibility Timeout.
        SQS absorbs/buffers the spike.
            buffer:
                SQS acts as a temporary storage area between the producer and consumer,
                allowing the consumer to process messages at its own pace.
            absorb the spike:
                Instead of the sudden traffic spike directly hitting and overwhelming the consumer,
                the queue accepts the messages and holds them until the consumer can process them.
        idea:
            SQS
            │
            └── Order A
                    │
                    ↓
            Shipping Service processing...
                    │
                    ├── SUCCESS → Delete message
                    │
                    └── FAILURE → message becomes visible again
                    So the order isn't simply lost.
        SQS Standard Queue:
            Oldest offering (over 10 years old)
            Fully managed service by AWS.
            Unlimited throughput
                queue ထဲရှိနိုင်တဲ့ message အရေအတွက်အတွက် unlimited
                massive scale အတွက် design လုပ်ထားတာ
            Default Rentention = 4 days, Max: 14 days.
                Retention: SQS က message တစ်ခုကို ဘယ်လောက်ကြာကြာ သိမ်းထားမလဲ ဆိုတာ။
                Consumer က Message A ကို မယူဘူးဆိုရင် SQS က forever သိမ်းထားမှာမဟုတ်ဘူး။
                Retention period ကျော်သွားရင် message ကို SQS က remove လုပ်နိုင်တယ်။
            Low latency (<10 ms(0.01 sec) on publish and receive):
            One SQS message can be up to 1,024 KB (1 MB).
                SQS ≠ S3
                Large file ကို SQS message ထဲ ထည့်ဖို့ မသင့်တော်ဘူး။
                ဥပမာ user က:
                video.mp4 = 500 MB
                ဆိုရင် SQS ထဲကို video file တစ်ခုလုံးထည့်တာ မလုပ်သင့်ဘူး။
                SQS message ထဲမှာ reference ပဲထားနိုင်တယ်:
                    {
                        "bucket": "my-video-bucket",
                        "key": "videos/video123.mp4"
                    }

                    ဒီလို architecture ကို SAA-C03 မှာ အများကြီးတွေ့ရတတ်တယ်။
                        Large object → S3
                        Small message / event → SQS
            at least once delivery
                SQS က message ကို အနည်းဆုံး တစ်ကြိမ်တော့ deliver လုပ်ပေးမယ် လို့ guarantee ပေးတယ်။
                ဒါပေမယ့်...
                တစ်ကြိမ်ထက်ပိုပြီး deliver ဖြစ်နိုင်တယ်။
                ဒါကြောင့် application က duplicate ဖြစ်ရင် ပြဿနာမဖြစ်အောင် design လုပ်သင့်တယ်။
            Messages can be many(Duplicate possible).
            Out of order(Best-effort ordering)
                Standard Queue က strict ordering ကို မ guarantee လုပ်ဘူး။
                Best effort = AWS က order ကို ထိန်းထားဖို့ ကြိုးစားတယ်, ဒါပေမယ့် 100% guarantee မပေးဘူး။
        FIFO Queue:
            FIFO = First In First Out(Messages are processed in the same order they were sent.)
            The idea is that batching allows multiple messages to be handled in one API operation.
                Without batching:
                    300 messages/second

                With batching:
                    3,000 messages/second
            Message deduplication:
                Deduplication ID:
                    producer can provide a: Message Deduplication ID
            Message Group ID:
                Ordering by Message Group ID(mandatory parameter)
                    SQS can maintain ordering for each Producer(customer) independently.
                    eg:
                        FIFO Queue
                        ────────────────────────────
                        Group A:
                        A1 → A2 → A3 → A4

                        Group B:
                        B1 → B2 → B3

                        Group C:
                        C1 → C2 → C3 → C4
                    This allows FIFO to have parallelism while preserving ordering within each group.
            Visibility Timeout still have.
        SQS with ASG:
            SQS acts as a buffer between a fast producer and a slower consumer.
            Remember:
                SQS Queue Length → CloudWatch Metric → CloudWatch Alarm → ASG Scaling → More/Fewer EC2 Consumers
            CloudWatch can monitor the queue and detect:
                Queue length = messages waiting to be processed
            Then CloudWatch can trigger an Alarm.
            Scale OUT.
            when the spike is over, Scale IN.
            architecture:
                 │    Producer   │
                 └───────┬───────┘
                         │
                    SendMessage
                         │
                         ▼
                 ┌───────────────┐
                 │   SQS Queue   │
                 │               │
                 │ 100 messages  │
                 └───────┬───────┘
                         │
                  Queue length
                         │
                         ▼
                 ┌───────────────┐
                 │  CloudWatch   │
                 └───────┬───────┘
                         │
                  threshold reached
                         │
                         ▼
                 ┌───────────────┐
                 │ CloudWatch    │
                 │    Alarm      │
                 └───────┬───────┘
                         │
                   Scaling action
                         │
                         ▼
                 ┌───────────────┐
                 │      ASG      │
                 │               │
                 │ EC2 #1        │
                 │ EC2 #2        │
                 │ EC2 #3        │
                 │ EC2 #4        │
                 └───────────────┘
                         │
                    Process SQS
                    messages
                SQS protects the consumer from the producer's sudden workload.
                CloudWatch monitors the queue backlog, while ASG automatically adjusts the number of workers.

        SQS Short Polling:
            consumer immediately gets the response.
            Then perhaps it asks again:
                10:00:00  → ReceiveMessage → No message
                10:00:01  → ReceiveMessage → No message
            This creates lots of API calls.
        SQS Long Polling:
            SQS, give me a message if one is available. If there isn't one yet, please wait for a while.
            eg:
                Consumer
                │
                │ ReceiveMessage
                │ WaitTimeSeconds = 20
                ▼
                SQS
                │
                │ ... waiting ...
                │
                │ Message arrives!
                ▼
                Consumer receives message
            Instead of immediately saying: "There are no messages."
            reduce API calls.
            WaitTimeSeconds:
                wait time can be between 1 sec to 20 sec
                20 seconds is generally preferred for long polling.
                20 sec is not exactly waiting time. SQS can return the message immediately.
                Queue-level configuration:
                    consumers can use long polling without specifying it on every request.
                        MyQueue
                            │
                            └── ReceiveMessageWaitTimeSeconds = 20
                API-level configuration:
                    consumer can controls the waiting behavior for particular API call.
        Important:
            SQS doesn't process the message.
            SQS itself isn't your business application.
                It doesn't say: "I'll ship the package."
                It only says: "I'll safely hold this message until a consumer processes it."
                So:
                    Producer
                    ↓
                    SQS
                    ↓
                    Consumer

                SQS = message storage / waiting line
                Consumer = does the actual work
            on AWS management console, 
                delete = Delete the entire SQS queue itself.
                purge = completely clean/remove the contents.
                    Delete all messages inside the queue, but keep the queue itself.
            Standard = high throughput, ordering not guaranteed
                🚀 Very high throughput
                ❌ Ordering not guaranteed
                ⚠️ Duplicate messages possible
            FIFO = ordering guaranteed, throughput is more limited
                Ordering + deduplication
                FIFO
                ├── 300 msg/s without batching
                ├── 3,000 msg/s with batching
                ├── Deduplication ID
                └── Message Group ID = mandatory
                Message Group ID → controls ordering lane
                Message Deduplication ID → detects duplicate sends
                Default deduplication scope → entire FIFO queue (can change on FIFO queue settings)
            SQS + ASG + CloudWatch + decoupling + database protection.

                | ------------------------------------------- | --------------------------------- |

                |                              | Short Polling                         | Long Polling     |

    SNS:
        Simple Notification Service
        message တစ်ခုကို receiver တစ်ယောက်တည်းဆီ ပို့တာမဟုတ်ဘဲ၊
        receiver အများကြီးဆီကို တစ်ပြိုင်နက်တည်း ဖြန့်ပို့ပေးတဲ့ service
        as a broadcast system.
        Explanation:
            With SQS:
                Producer
                ↓
                SQS Queue
                ↓
                Consumer
                Usually, a message in a queue is processed by one consumer.
            With SNS:
                                ┌──→ SQS Queue
                                │
                Producer → SNS Topic
                                │
                                ├──→ Lambda
                                │
                                ├──→ Email
                                │
                                └──→ HTTP endpoint
                One message can be delivered to multiple subscribers.
        Topic:
            a communication channel that 
            publishers send messages to and subscribers receive messages from.
            Note:
                event producer only sends message to one SNS topic.
                producer doesn't need to know who is listening.
                    The producer doesn't directly communicate with:
                        Payment Service
                        Shipping Service
                        Email Service
                        Analytics Service
                    This is an important part of decoupling.
        Publisher:
            application that sends a message to SNS.
        Subscriber:
            Something that receives messages from the SNS Topic.
                eg:
                    SQS
                    Lambda
                    HTTP/HTTPS endpoint
                    Email
                    SMS
            subscription:
                Each one receiver creates a subscription to the SNS topic.
                A subscription basically means:
                    "I want this destination to receive messages from this SNS Topic."
                Subscriber = who receives
                    The destination that wants the messages.
                Subscription = the connection saying they want to receive
                    The relationship connecting that destination to the SNS Topic.
            One message published to SNS → every subscription receives a copy.
                This is the fan-out pattern.
                massive fan-out:
                    One topic can have a huge number of subscriptions: 12500,000/topic.
                    aws account has a service quota: 100,000 topics limit.
        Why do we need SNS?
            Imagine you have an e-commerce application.
            When an order is created, several things need to happen:
            Order Created
            You need to:
                Process payment
                Send confirmation email
                Update inventory
                Generate shipping task
                Send analytics event
            Without SNS:
                    Order Application
                    ├──→ Payment
                    ├──→ Email
                    ├──→ Inventory
                    ├──→ Shipping
                    └──→ Analytics
                The application needs to know about every downstream service.
                This creates tight coupling.
            With SNS
                Instead:

                                    SNS
                            OrderCreated Topic
                                    │
                    ┌───────────────┼───────────────┐
                    ↓               ↓               ↓
                    SQS             Lambda          SQS
                Payment          Email           Inventory
                    │
                    ↓
                Payment Service

                The original application only needs to know: "Publish OrderCreated to SNS."
                It doesn't need to directly communicate with every service.
                This is decoupling.
        SNS = Pub/Sub
            Pub = Publish
            Sub = Subscribe
            flow:
                Publisher
                    ↓
                Publish
                    ↓
                SNS Topic
                    ↓
                Subscribers

                    ↓
            Process in real time
        Steaming Data:
            Streaming data means data that arrives continuously over time
                rather than being collected as one large batch.
        Producers:
            sends data into Kinesis.
        Applications:
            own app can use the Kinesis SDK/API to send records.
        Kinesis Agent:
            software that can collect data such as logs from servers
        Kinesis Data Streams:
            central part.
            Kinesis stores incoming records in a stream like a continuous conveyor belt.
            continuous conveyor belt = စဉ်ဆက်မပြတ် သယ်ယူပို့ဆောင်ရေးခါးပတ် in industry/airport.
            Rention: configurable up 365 days
                Data remains in Kinesis even after a consumer reads it. supports replay.
                Replay = read previously processed streaming data again.
                Data can't be deleted from Kinesis.
                    consumers don't individually delete records.
            Data up to 10 MiB:
            Ordering guarantee with the same Partition ID:
                Same partition key → same partition → ordering preserved.
            Encryption:
                In-flight: HTTPS
                at-rest: KMS
            Kinesis Producer Library (KPL):
                Producer side.
                an optimized application that writes data to Kinesis.
            Kinesis Client Library (KCL):
                Kinesis Client Library
                optimized application that reads/processes data from Kinesis.
            Cheat sheet:
                | Feature                  | Remember                         |
                | ------------------------ | -------------------------------- |
                | Purpose                  | Real-time streaming data         |
                | Data examples            | IoT, clickstreams, logs, metrics |
                | Retention                | Up to **365 days**               |
                | Consumer reads data      | Data **isn't deleted**           |
                | Replay                   | ✅ Yes                            |
                | Delete individual record | ❌ No                             |
                | Expiration               | When retention period expires    |
                | Maximum record size      | **10 MiB**                       |
                | Ordering                 | Within the **same partition**    |
                | Encryption in transit    | HTTPS                            |
                | Encryption at rest       | KMS                              |
                | Producer library         | **KPL**                          |
                | Consumer library         | **KCL**                          |
            Capacity Modes:
                Provisioned = You choose/manage the capacity.
                    choose how many shards your Kinesis stream has.
                    Each shard has a certain capacity.
                    Per shard
                        Write/Ingestion: 1 MB/s
                        Read/Output: 2 MB/s
                    What does "shard" mean?
                        shard as a capacity unit / lane.
                    Scaling:
                        Manual
                        AWS doesn't automatically change your shard count based on your traffic.
                    Cost:
                        pay based on the number of shards provisioned.
                            1 shard → $$$
                            5 shards → $$$$$
                On-demand = AWS chooses/scales the capacity for you.
                    Scaling: 
                        AWS automatically manages capacity
                    Default capacity provisioned: 4 MB/s in or 4,000 records/s
                Note:
                    |                       | **Provisioned** | **On-demand**          |

                    | Predictable traffic   | ✅ Good          | ✅                   |
                    | Unpredictable traffic | More management | ⭐ Good               |
                    | Cost                  | Per shard/hour  | Per stream/hour + data |

            reads/processes data from Kinesis.

                own Application,

                Amazon Data Firehose

                        analytics
                        detecting patterns
        Why not just use SQS?
            on SQS: Producer → SQS → Consumer
                think: "I have work that needs to be processed."
                Consumer processes the order and eventually deletes the message.
            on Kinesis: Producer → Kinesis → Consumer
                think: "I have a continuous stream of events/data that multiple consumers may want to process."
                Multiple applications can consume the stream independently.
            Their purposes are different. major reason Kinesis is useful.
        Kinesis Data Streams vs SNS:
            SNS => Publish/Subscribe → notify subscribers
            Kinesis => Streaming data collection + real-time processing
            think:
                SNS → "Something happened. Tell interested subscribers."
                Kinesis → "Here is a continuous stream of data. Process/analyze it."
        Note:
            SQS = queue model
            SNS = pub/sub model
            Kinesis = real-time streaming model.

                SQS

                └─ Queue work
                "Process this job."

                SNS
                │
                └─ Pub/Sub
                "Tell everyone interested."

                Kinesis Data Streams
                │
                └─ Streaming data
                "Continuously collect and process this data."

        Cold Start:
            Lambda needs to prepare a new execution environment before running your function.

                AWS creates an execution environment for your function.
                    Lambda Function

                        ↓
                    Execution Environment
                        │

                    Warm Start:
                        very little setup is required.
                        Low latency.
                        flow:
                            Request
                            ↓
                            Existing Lambda environment
                            ↓
                            Handler
                            ↓
                            Response
                    Cold Start:
                        if not have a ready execution environment.
                        higher latency.
                        flow:
                            Request
                            ↓
                            Create new execution environment
                            ↓
                            Load runtime
                            ↓
                            Load your code
                            ↓
                            Load dependencies
                            ↓
                            Run initialization
                            ↓
                            Handler
                            ↓
                            Response
                        That preparation takes additional time.
                    Why doesn't every request cause a Cold Start?
                        lambda get request:
                            Request 1
                            ↓
                            Cold Start
                            ↓
                            Environment A

                            Request 2
                            ↓
                            Environment A
                            ↓
                            Handler

                            Request 1 → 🥶 Cold
                            Request 2 → 🔥 Warm
                            Request 3 → 🔥 Warm
                            Request 4 → 🔥 Warm

                        Then:
                            Request 5
                            ↓
                            New environment
                            ↓
                            🥶 Cold Start
                        Sudden traffic spike can cause:
                            Cold-start latency

        IAM integration
        Low cost + auto-scaling
            capacity modes
                Provisioned capacity(default):
                    can set reads/writes per seconds.

        Basic:
            DynamoDB is made of Tables
            Each table stores a collection of items.
                Maximum item size = 400 KB
            Table → Item → Attribute
                | SQL    | DynamoDB      |
                | ------ | ------------- |
                | Table  | Table         |
                | Row    | **Item**      |
                | Column | **Attribute** |
                Attributes don't have to be identical.
                    This is called a flexible schema.
            Every DynamoDB table must have a Primary Key.
                Primary Key must be decided when the table is created.
            Partition Key:
                an attribute used to identify and distribute items.
            Sort Key:
                second key that can be used together with the Partition Key.
            Simple Primary Key:
                Simple Primary Key contains only a Partition Key.
            Composite Primary Key:
                Partition Key + Sort Key
        Data Types:
            Scalar Types
                Scalar means basically one value.
            Document Types
                List,Map to allow you to create nested structures.
                List => array
                Map => Object / Dictionary.
            Set Types
                collection of unique values of the same type.
                    String Set
                    Number Set
                    Binary Set
        can repidly evolve schemas:
            DynamoDB has a flexible schema at the item/attribute level.
                but, Primary Key is NOT flexible.
        DynamoDB Accerlerator(DAX):
            Sits in front of DynamoDB to cache frequently read data.
            flow: Application → DAX → DynamoDB
            Helps reduce read congestion on DynamoDB.
            Cached data can be returned in microseconds.
            No application code changes required because DAX is compatible with existing DynamoDB APIs.
            Default TTL = 5 minutes.
            DAX vs ElastiCache:
                DAX → specifically designed for DynamoDB, minimal/no application changes.
                ElastiCache → general-purpose Redis/Memcached cache;
                    usually requires application-level caching logic.
        DynamoDB - Stream Processing:
            DynamoDB Streams / Kinesis Data Streams can capture item-level changes in DynamoDB.
            stream:
                A record of changes happening to items in your DynamoDB table.
